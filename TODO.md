# Bar Management System — Fix Checklist

Generated from a full codebase review on 2026-07-23. Check items off as they're fixed.

## Critical

- [x] **Customer QR orders trust client-submitted prices.** `customer/order.php` (`submit_order`) takes price/quantity straight from the posted JSON cart with no server-side re-lookup against `bar_menu_items`. A customer can edit the request and order anything at any price. Fix: look up `id`, `active`, `price` server-side per item; ignore client-supplied price entirely.
  - **Fixed 2026-07-23**: cart is now reduced to `{id, qty}` pairs server-side (client `price`/`name` fields are ignored), quantities are merged per item and capped at 50/line, and price/availability are re-fetched from `bar_menu_items WHERE active = 1` in one query. If any submitted id isn't found active, the whole order is rejected with "items no longer available" rather than silently dropped.

## High

- [x] **Refunds aren't capped against amount paid.** `pages/pos.php` `refund` action computes a `$paid` total then discards it (`// simpler: just insert and trust the manager`). Nothing stops a refund exceeding what was actually paid.
  - **Fixed 2026-07-23**: the entire refund handler in `pages/pos.php` was dead code (unreachable — no form on that page ever posted `action=refund`; the modal was an empty stub). Removed it. The real, UI-wired handler in `pages/orders.php` now calls a new `remainingRefundable($orderId)` helper (`includes/functions.php`) and rejects any refund exceeding `paid − already refunded`. The refund modal's amount field also gets a `max` attribute from the actual remaining balance client-side.
- [x] **Refunds never reduce reported revenue.** `bar_refunds` rows are never subtracted in `pages/reports.php` or `pages/reconciliation.php` — sales/cash totals are overstated once refunds happen.
  - **Fixed 2026-07-23**: added a `method` column to `bar_refunds` (schema + migration ALTER — **needs to be applied to the live DB**, see note below) so we know whether a refund came out of the cash drawer or elsewhere. `pages/reports.php` now shows Refunds and Net Sales stat cards for the selected period. `pages/reconciliation.php` now nets cash refunds out of expected cash and all refunds out of shift net sales (added `total_refunds` column to `bar_shift_reconciliation`, patched in via `ADD COLUMN IF NOT EXISTS` so existing installs pick it up automatically), and shows refunds in the live shift view, the closed-shift summary, and the shift history table.
  - **Migration applied 2026-07-23** directly against the live `school_db` database — verified via `DESCRIBE`, row counts unchanged (0 refunds, 0 shifts).
- [x] **Stock limits are UI-only.** The disabled "out of stock" button in POS is cosmetic — `add_item` in `pages/pos.php` never checks `stock_state` server-side before adding an item to an order.
  - **Fixed 2026-07-23**, two layers:
    - Quick gate: new `isMenuItemOutOfStock()` helper (`includes/functions.php`) mirrors the same rule used for the UI badge. `add_item` now rejects out-of-stock items server-side, and `update_qty` blocks *increasing* a line's quantity past stock (decreasing/removing is still always allowed).
    - Real backstop: added `checkStockAvailability()` in `pages/pos.php`, which locks the relevant `bar_inventory` rows with `FOR UPDATE` inside the checkout transaction and re-verifies availability right before payment is recorded. This is what actually matters — it closes the race where two staff sell the last unit of something to two different tables at the same moment; the second checkout to reach the lock now sees the depleted quantity and is rejected with a clear "out of stock" redirect instead of silently overselling.
    - Not done (flagged as a known limitation, not a bug): stock isn't *reserved* the moment an item is added to a cart, only checked. Two staff can still both have the last unit sitting in their carts simultaneously — checkout is what decides who actually gets it. Building true reservation/holds would be a bigger change than this fix calls for.
- [x] **Payment idempotency is broken.** `customer/receipt.php`'s "INSERT IGNORE prevents race-condition double-insert" comment is false — `bar_payments.reference` has no `UNIQUE` constraint in the schema, so `IGNORE` does nothing. Add a unique index on `reference` (excluding NULLs) or use an application-level lock.
  - **Fixed 2026-07-23**: added `UNIQUE INDEX uq_bar_payments_reference` on `bar_payments.reference` in `database/schema.sql`. MySQL treats each `NULL` as distinct under a unique index, so staff cash/card/transfer payments (which have no reference) are unaffected — only duplicate *non-null* Paystack references are rejected. This makes `receipt.php`'s existing `INSERT IGNORE` comment actually true for the first time.
  - **Migration applied 2026-07-23**: checked for existing duplicate references first (none found — only 2 payment rows existed), then added the unique index directly against the live database. Verified with `SHOW INDEX`.
  - **Also discovered while applying this**: the `ADD COLUMN IF NOT EXISTS` / `ADD UNIQUE INDEX IF NOT EXISTS` syntax used in `database/schema.sql` and in `reconciliation.php`'s self-patch doesn't actually work on this server's MySQL (8.0.46) — confirmed with a throwaway-table test, it's a hard syntax error, not a no-op. Both were rewritten to use syntax that actually runs here (plain `ADD COLUMN`/`ADD INDEX` for the one-time migration; `SHOW COLUMNS ... LIKE` as a manual existence check in the self-patch). Note: older `ADD COLUMN IF NOT EXISTS` statements already in `schema.sql` from before this session (the `bar_orders` additions) have the same latent problem, but those columns already exist on this database so it's moot here — only matters if the schema is ever run fresh against a new install.
- [x] **Same idempotency gap in the Paystack webhook.** `webhook/paystack.php` has no dedupe check at all before inserting into `bar_payments` — a retried webhook delivery can double-record a payment.
  - **Fixed 2026-07-23**: added the same pre-check pattern already used in `receipt.php` (skip if `reference` already recorded) as a fast path, backed by the new `UNIQUE` constraint as the authoritative guard for two near-simultaneous deliveries. The catch block now `error_log`s unexpected failures instead of swallowing everything silently, since a webhook has no user to show an error to.
- [x] **No ownership check on customer-facing order pages.** `customer/order.php` and `customer/receipt.php` trust whatever `order_id` is in the URL with no tie-back to the session/table that created it — anyone can view another table's order/payment status by changing the number.
  - **Fixed 2026-07-23**: added `fetchOwnedOrder($orderId, $token)` in `includes/functions.php`, which only returns an order if the given table QR `token` actually matches the table that order belongs to (a wrong token is treated identically to a nonexistent order, so it can't be used to probe which order ids exist). Applied to `customer/order.php` (both the page view and the `ajax=status` polling endpoint) and `customer/receipt.php`. Also fixed a related gap this surfaced: the Paystack payment callback in `customer/order.php` wasn't forwarding the table `token` to `receipt.php` at all, which would have broken the new check for every online payment — it now does.
  - Didn't tie this to the PHP session (`customer_session`) instead, deliberately: multiple phones can scan the same table's QR and should all be able to see that table's order status, and they don't share a session/cookie. The table token is the right unit of ownership here, matching how every other customer-facing link in the app already works.

## Medium

- [x] **Dead "new order" toast on POS.** `public/js/pos.js` polls for new customer orders but looks for `[name="active_order_id"]`, an element never rendered in `pages/pos.php` — the check always short-circuits and the notification never fires.
  - **Fixed 2026-07-23**: removed the broken guard. `pos.js` is only ever loaded on `pages/pos.php` (it's the only place that includes the script), so the poller now simply runs whenever the POS page is open, which was the actual intent.
- [x] **Duplicated pages.** `pages/tables.php` and `pages/qr-codes.php` are near-identical (same table CRUD + QR rendering, copy-pasted action handlers). Consolidate into one.
  - **Fixed 2026-07-23**, scoped narrowly: the two pages serve genuinely different purposes (a "manage tables" screen vs. a "print QR sheet" screen) and are both separate items in the sidebar nav, so I didn't merge the pages themselves — that's a product/IA decision, not a cleanup. What *was* pure duplication (the `add_table`/`edit_table`/`toggle_table`/`regenerate_token` POST handlers — byte-identical between the two files except which page they redirected back to) is now a single shared `includes/table_actions.php`, included by both. It redirects back to whichever page called it via `basename($_SERVER['SCRIPT_NAME'])`, so behavior and URLs are unchanged.
- [x] **Router is missing 4 of its own pages.** `index.php`'s `$allowedPages` omits `suppliers`, `reconciliation`, `inventory-mapping`, `audit-log` — they only work via direct `/bar/pages/x.php` URLs, not `/bar/?page=x`.
  - **Fixed 2026-07-23**: all four added to `$allowedPages`.
- [x] **Unhandled duplicate-email crash.** `pages/staff.php` `add_staff` has no try/catch around the insert — a duplicate email hits the DB `UNIQUE` constraint and produces a raw PHP fatal error instead of a friendly message.
  - **Fixed 2026-07-23**: both `add_staff` and `edit_staff` (which had the same gap — editing an account's email into collision with another wasn't handled either) now catch `PDOException`, distinguish a duplicate-key error from anything else, and redirect with a friendly banner instead of crashing.

## Low / cleanup

- [x] Remove dead "compute then discard" code: the abandoned `$paid` calc in `pages/pos.php` (`refund` action) — *removed 2026-07-23 along with the whole dead handler, see High section above.*
- [x] Remove the duplicate count query in `pages/audit-log.php` that's immediately overwritten by the correct one below it. — *removed 2026-07-23.*
- [x] `bar_tables.status` has a `reserved` enum value that's never set anywhere in the UI — either build the reservation workflow or drop the unused state.
  - **Built 2026-07-23** (user chose "build the workflow" over dropping it, scoped to a plain status toggle — no reservation details/notes): added a `toggle_reserved` action to `includes/table_actions.php` (guards against reserving an already-occupied table) and a Reserve/Un-reserve button on `pages/tables.php`'s table cards, shown whenever a table is `free` or `reserved`. Turns out `public/css/style.css` already had a fully-styled `.table-btn.reserved` state waiting for this — it was built once and never wired up. No changes needed in `pages/pos.php`: its table-selection grid already disables anything that isn't `free`, so a reserved table is automatically blocked from new walk-in orders the same way an occupied one is.

## Missing features worth considering

- [x] Cost/margin (COGS) report — `cost_price` is tracked in inventory but never joined against sales revenue anywhere.
  - **Built 2026-07-23**: `pages/reports.php` now computes per-item cost/margin (only for items whose full inventory mapping has a `cost_price` set — items with no/incomplete mapping show "—" rather than being assumed free) and adds Cost-of-Goods-Sold + Gross Profit stat cards, a "Profit Margin by Item" table, and cost/margin columns in the items CSV export.
- [x] Password reset flow for staff (currently admin must manually re-set via Edit).
  - **Built 2026-07-23** (user chose: admin-generated one-time link, no email server): added `bar_users.reset_token`/`reset_token_expires` (hash of the token stored, never the raw token), a "Reset Link" button per staff row in `pages/staff.php` that generates a 24-hour one-time link via a session flash message, and a new public `reset-password.php` page for the staff member to set their own new password.
- [x] Thermal/ESC-POS printer integration — receipts currently only go through the browser print dialog.
  - **Built 2026-07-23** (user chose: USB-connected printer; targeted Linux since that's this dev environment): `includes/escpos.php` builds the raw ESC/POS byte payload (plain ASCII `NGN 1,234.50` instead of `₦` — most thermal printers can't render multi-byte UTF-8 on their default codepage); `bin/print-agent.php` is a standalone local agent (run separately, on the POS terminal itself) that a browser can POST that payload to, which then writes it to the printer device; a "Print via Thermal Printer" button was added next to the existing browser-print button in `pages/pos.php`. Full setup/troubleshooting in `PRINTING.md`, including a systemd unit to keep the agent running. Verified the agent's HTTP handling and device-write logic against a fake device file (byte-for-byte correct output) — **not tested against real printer hardware**, since none is available here.
- [x] Real customer email passed to Paystack (currently hardcoded `customer@bar.com`, so Paystack's own receipt emails go nowhere useful).
  - **Built 2026-07-23** (user chose: prompt the customer): added an optional email field to the pay screen in `customer/order.php`. If left blank, falls back to a per-order-unique placeholder (`order-{id}@noemail.local`) instead of the same literal fake address every time.
- [x] Login rate-limiting/lockout — no brute-force protection on staff login, which is internet-reachable since Paystack webhooks need to reach the server.
  - **Built 2026-07-23**: new `bar_login_attempts` table logs every login attempt (success or fail). `login()` in `includes/auth.php` checks recent failures *before* touching the password at all — 5 failed attempts for the same email or 20 for the same IP within a 15-minute window blocks further attempts with a friendly message. Old rows are garbage-collected opportunistically (no cron job in this app).
- [x] Automated tests — none exist anywhere in the project.
  - **Built 2026-07-23** (user chose: pure logic only, no DB): set up Composer + PHPUnit 11 from scratch (`composer test` to run). 22 tests across `e()`/`money()`/CSRF token handling/`calcTax()`/`calcTotal()`, all passing with **zero database connection** required.
  - Two small refactors made this possible: (1) `includes/db.php`'s PDO connection is now lazy (only connects on the first actual `db()` call, not merely when the file is required) — previously just requiring `functions.php` for a test as simple as `money()` would force a live DB connection. (2) `calcTax()`/`calcTotal()` now accept an optional explicit `$rate` parameter (defaults preserve exact existing behavior for every current caller) so the actual percentage/rounding math is testable without touching `getSetting()`/the database.
  - Not covered (documented as a deliberate limitation, not a gap left by accident): `verifyCsrf()`'s failure path can't be safely unit-tested since it calls `die()`, which would kill the test runner; and anything DB-integration-shaped (`remainingRefundable()`, `isMenuItemOutOfStock()`, `checkStockAvailability()`, the full checkout/refund flows) is genuinely integration-test territory, which the user explicitly scoped out of this round.
